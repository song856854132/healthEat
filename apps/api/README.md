# @healtheat/api

Express 5 REST API, deployed as one Vercel function (zero-config Express; entry `src/app.ts`).

Nothing changes; rename the entry with `PUT` instead                                                                                                                                                                                                          |
| `404 {error: "token_not_found"}`                                                                 | `PUT /api/curate/unmatched/:token` for a phrase the queue does not hold (the path is normalised first, so case and spacing do not matter)                                                                                                                                                                                                                                  |
| `409 {error: "token_mapped"}`                                                                    | `ignore` on a queued phrase that is already mapped to an allergen; nothing is written                                                                                                                                                                                                                                                                                      |
| `409 {error: "token_excluded"}`                                                                  | `map` to an allergen whose exclude phrases hide the phrase, so it could never match; nothing is written                                                                                                                                                                                                                                                                    |
| `409 {error: "synonyms_full"}`                                                                   | `map` to an allergen that already holds 200 synonyms (not counting this phrase); nothing is written                                                                                                                                                                                                                                                                        |
| `403 {error: "account_suspended"}`                                                               | `status` is not `active`: login refused, and an existing session is destroyed on its next request                                                                                                                                                                                                                                                                          |
| `403 {error: "account_deletion_pending"}`                                                        | `deletionPending` is set (T5 cascade in progress); same handling as suspended, except that login with the right password first finishes the deletion (below)                                                                                                                                                                                                               |
| `409 {error: "username_reserved"}`                                                               | `POST /api/auth/register` with a username listed in `ADMIN_USERNAMES`: a listed name is never claimable through open registration; create the account before listing it                                                                                                                                                                                                    |
| `409 {error: "cannot_revoke_own_admin"}`                                                         | an admin tried to remove `admin` from their own account (prevents locking every admin out)                                                                                                                                                                                                                                                                                 |
| `409 {error: "last_admin"}`                                                                      | the change would leave no usable admin (active, not being deleted), checked before and after the write, so two admins demoting or suspending each other cannot both win; also `DELETE /api/users/me` by the only usable admin                                                                                                                                              |
| `409 {error: "roles_changed"}`                                                                   | another admin changed the same account's roles between this request's read and write; reload and retry                                                                                                                                                                                                                                                                     |
| `409 {error: "cannot_suspend_self"}`                                                             | an admin tried to suspend their own account                                                                                                                                                                                                                                                                                                                                |
| `409 {error: "cannot_delete_self"}`                                                              | `DELETE /api/admin/users/:username` named the caller; an admin deletes their own account with `DELETE /api/users/me`                                                                                                                                                                                                                                                       |
| `404 {error: "not_found"}` (admin routes)                                                        | an `/api/admin/users/:username` route named an unknown username                                                                                                                                                                                                                                                                                                            |
| `400 {error: "username_immutable"}`                                                              | `PUT /api/users/me` with a `username` in the body; the username never changes                                                                                                                                                                                                                                                                                              |
| `404 {error: "user_not_found"}`                                                                  | `GET /api/users/:username` for an unknown, malformed, suspended or deleting account                                                                                                                                                                                                                                                                                        |
| `403 {error: "forbidden"}`                                                                       | the account does not hold the role a route needs (`requireRole` checks `roles`, never `activeRole`), asks for an active role or a role profile it does not hold, or edits a log entry that is not its own                                                                                                                                                                  |
| `500 {error: "internal"}`                                                                        | anything else; logged with its stack, `details` only on local runs                                                                                                                                                                                                                                                                                                         |

`GET /api/health` never forces a connection and reports `db` (`connected`, `connecting`, `disconnected`,
`unconfigured`, `misconfigured`), the non-secret `dbName`, and `secrets` (`ok` or `missing`).
`GET /api/health/db` forces a live connection and answers `503 database_unavailable` unless the
connection state is `connected` (a cached promise that survived a drop never yields a 200); the staging
and release smokes check it together with `secrets: "ok"` on `/api/health`. Details on 5xx
responses are redacted on every deployment (`isDeployed()`), shown only on local runs, unless the
`HttpError` was raised with `expose: true` because its details are written for users (today
`usda_unavailable` and the photo errors `vision_unavailable`, `vision_failed` and `vision_timeout`).

Sessions: `express-session` + `connect-mongo`, collection `sessions` in the same database, 14-day TTL,
rolling, written at most once a day per session (`touchAfter`). Cookie `he_sid`: `HttpOnly`, `SameSite=Lax`,
`Secure` on every deployment, no domain (same origin through the Next.js rewrite). Session data is
`{userId, activeRole}`, stored as a document (not a JSON string) so T5 can delete a user's sessions by
`session.userId`. Passwords: `bcryptjs` cost 12 (pure JavaScript: no native module to build for the
function's architecture); never returned (`passwordHash` has `select: false`).

Login throttle (design doc D7): `LoginAttempt {key, count, windowStart}` counts login attempts per
lowercased username plus `req.ip`. Each attempt is counted atomically before the bcrypt compare, so
unknown usernames and wrong passwords both count and a burst of parallel requests gets at most 10
compares. After 10 failures inside a 15-minute window that starts at the first one, login answers
`429 too_many_attempts` with `Retry-After` and no compare, even for the right password. A successful login
deletes the counter, and a TTL index on `windowStart` removes stale windows. The limit is per username
and client IP, with no ceiling per account. Through the Next.js rewrite, `req.ip` (`trust proxy` 1) may be
one shared Vercel hop, which makes the key effectively per username: anyone can then lock an account's
logins for up to 15 minutes. A client that calls the public API origin directly is keyed by its own IP,
so an attacker who rotates IPs gets 10 guesses per address.

USDA proxy (design doc D5, S7): `/api/foods/*` needs the database (for its caches and, on details, the
local data) but no session. Search never reads one; `GET /api/foods/:fdcId` reads it when the caller
sends one, to add the signed-in parts of `localStats` (T28).
A search page is stored in `searchcaches` (`SearchCache {key, payload, createdAt}`, key = lowercased
query, data type and page) and served without calling USDA for one hour; a TTL index deletes it after 24
hours. Opened foods are stored in `foods` (`Food`, unique `fdcId`) and re-fetched after 30 days; they are
never deleted, because log entries will point at them. When USDA fails, the stored copy is served with
`cached: true`; with nothing stored the route answers `503 usda_unavailable`. Search does not store the
foods on its result page; only a food someone opens is stored. A query USDA rejects (400) answers an
empty result page. A stored page or food that no longer matches the response shape is refetched. The
routes have no abuse limit yet (accepted risk, TODOS.md "Food routes: abuse limit and cache footprint").

Allergen dictionary and matcher (design doc: Allergen matching, D12; T11): `allergens` (`Allergen {key,
displayName, tier, synonyms, descriptionKeywords, excludePhrases, source, updatedBy}`) is seeded from
`ALLERGEN_SEED` (`packages/shared`, provenance in `packages/shared/data/PROVENANCE.md`) when it is first
read. A marker document (`dictionaryseeds`) lists the seed keys already written; any seed key missing
from it is upserted on the next read, so a partial first seed is finished and a later seed addition
reaches existing databases. The seed never overwrites an entry, and a seed entry a Curator deleted stays
deleted.
Each opened food is matched once per USDA copy and its rows are stored in `foodallergens` (`FoodAllergen
{fdcId, allergenId, matchKind, matchedSynonym, matchedAt}`, unique per food and allergen). The ingredient
text is split at commas, semicolons, colons, periods and brackets, and a synonym must match whole words
inside one ingredient (`ingredient`). The description is searched for `descriptionKeywords` when the food
has no ingredient text, and for sensitivity-tier allergens on every food (`description`, shown with the
label "food-category estimate"). An exclude phrase hides its words from that allergen only ("cocoa butter"
is not milk). `Food.allergensMatchedAt` is set after the rows are written; a food without it (cached before
T11, a failed write, or a dictionary that kept changing during the match) is matched again on its next read.
A dictionary edit reaches already matched foods only through the re-match pass (T5).

Log routes (design doc A2, R3-25 to R3-27; T6): `logentries` (`LogEntry {userId, date, meal, fdcId, grams,
source, confidence, photoBatchId, requestId, createdAt}`, indexes `{userId, date}`, `{date}` and `{fdcId, date}`,
the last for a food's local data, T28, plus a unique `{userId, requestId}` index limited to entries that carry a
`requestId`, which makes the create idempotent, #51) and `userallergens`
(`UserAllergen {userId, allergenId, mode, weeklyThreshold}`, unique per member and allergen). Listing,
creating and allergen settings live under `/api/users/me/*`, so no log or settings route names another member; `PUT/DELETE
/api/logs/:id` pass `requireOwner`, which answers 404 `log_not_found` for an id that names no entry and 403
`forbidden` for another account's entry, whatever roles the caller holds. `date` is the member's calendar
day in their `MemberProfile.timezone` (UTC when unset). An entry's date and food are fixed once logged; a
wrong food is deleted and logged again. Hard alerts compare the food's `allergens[]` (T11) with the
member's avoid-mode settings.

Summary (design doc, Core algorithms; T25): `GET /api/users/me/summary` (`services/summary.ts`) computes
the week on read from the member's `LogEntry` rows, with no stored totals. Bands average over logged days
only, and a food that does not report a nutrient counts against that band's `dataCoverage` (below 50% the
band is `insufficient`). Targets come from `packages/shared/src/dri.ts` (provenance in
`packages/shared/data/PROVENANCE.md`). The calorie meter and the alerts always use today in the member's
time zone, also when `weekEnding` names a past week; an alert is listed once per avoided allergen and food,
however often the food was logged today. Allergens come from `allergensForFoods`, one batched read for
the week's matched foods; foods not matched yet are matched five at a time.

Deletion and re-match (design doc D6, R3-3, R3-4; T5): no Mongo transactions, every step rerunnable.
Account deletion (`services/account.ts`, shared by `DELETE /api/users/me` and the Admin delete of T21) sets
`User.deletionPending` first, so login and every session of the account answer `403
account_deletion_pending` from then on; then it deletes the account's `LogEntry`, `UserAllergen`, the three
role profiles and its `sessions` documents, then the `User`, then the logs and settings once more (a write
that passed `requireAuth` before the flag). The route retries a failed cascade once; if that fails too the
account stays locked, and the member's next login with the right password finishes the deletion before
answering 403. The only usable Admin (active, not being deleted) gets `409 last_admin`, checked before and
after the flag with `usableAdminCount` (the same count as role changes); a refusal clears the flag, so a
flagged last Admin's next login calls the deletion off and signs them in. `DELETE /api/allergens/:id`
first refuses with 409 while the entry exists and any member avoids it (#52), then deletes the allergen's `FoodAllergen` and `UserAllergen` rows, then the entry, then its `FoodAllergen` rows
once more (a food matched meanwhile); a retry after the entry is gone still sweeps its rows, avoid settings included, before answering
404, and a re-match that finds its allergen gone drops the rows it wrote. After a dictionary edit,
`startRematch` sets `Allergen.rematchCursor` to 0 (the next fdcId to process) and bumps `rematchRun`;
`rematchAllergen` walks the cached foods in fdcId batches of 500, one ordered `bulkWrite` per batch (delete
the allergen's rows for the foods the batch read, insert the new matches), and moves the cursor only if
neither the cursor nor the run changed meanwhile. It stops after 60 seconds with `{done: false, processed,
remaining}` and resumes from the cursor; null means done. A food cached and matched by another request while
a batch runs keeps its rows, and `matchAndStore` reads the dictionary version (each entry's id and
`rematchRun`) again after its write: if a Curator add, edit or delete landed meanwhile (its re-match or its
last row sweep may already have passed the food), the food is matched once more against the new dictionary,
which also drops a deleted entry's row; if the dictionary moves again, the food is left unstamped and its
next read matches it. A batch likewise reads `rematchRun` and its foods' `fetchedAt` again after its write:
if a newer edit's re-match or a USDA refresh of one of its foods landed meanwhile, it writes the batch once
more from the newer entry and copies; if they move again, the foods that may hold stale rows (the whole batch
after a newer edit, only the refreshed foods otherwise) are left unstamped and the next read of each matches
it against the current dictionary. A batch whose write stops at a concurrent writer's duplicate key leaves
its foods unstamped, then repeats from the cursor, and stops at the 60-second budget like any other.

Curator and Admin (T21, D18): `POST /api/allergens` and `PUT /api/allergens/:id` start the re-match in the
same write (the new entry is inserted with cursor 0; an edit sets it to 0 and bumps `rematchRun` in its
update), so a request that dies before the first batch leaves the entry `rematchPending` instead of stale,
and run the pass in the same request. Every edit restarts it, a rename included: deciding from a read made
before the write would race a concurrent edit. The Admin routes act through the same guards as role
changes: no Admin suspends or deletes themselves, and a suspension that would leave no usable Admin is
undone and refused. Suspension deletes the account's sessions; Admin delete is `deleteAccount` with
`keepAnAdmin`.

Unmatched-ingredient queue (T22, design doc `IngredientToken`): after `matchAndStore` stamps a food, each
ingredient segment of 3 to 80 characters that matches no synonym of any entry (exclude phrases applied) is
recorded as an `IngredientToken`, with one `IngredientTokenFood {token, fdcId}` row per token and food
(unique), so `count` is the number of distinct foods and `sampleFdcIds` keeps the first 5. There is no
backfill: counts start when this release is deployed, and a food matched before it is recorded only when it
is matched again (its 30-day USDA refresh, or a read after its stamp was cleared). The re-match pass does
not record tokens, so a phrase a later Curator edit makes matchable stays in the queue (TODOS.md "Unmatched
queue: retire tokens a later dictionary edit makes matchable").

Privacy acknowledgment: the banner sets the readable cookie `he_privacy_ack` (1 year, `SameSite=Lax`).
Register and login copy it to `User.privacyAckAt` when present, and set it when the account already has
`privacyAckAt` (new device). `MeResponse.user.privacyAckAt` tells the web whether to show the banner.

Session-backed routers are mounted as `requireDb, sessionMiddleware(), router`: a database that does not
answer gives `503 database_unavailable` before the session store is touched. `/api/health` and the spike
routes never open a session. `/api/foods` is mounted as `requireDb, router`; only `GET /api/foods/:fdcId`
adds `sessionMiddleware()` on its own route, so search never touches the session store.

```bash
set -a; . ~/.env.staging; set +a      # on the VM; locally use .env.example values
npm run dev -w @healtheat/api         # http://localhost:4000/api/health
npx vitest run --project api          # tests start an in-memory MongoDB per worker
npx vitest run --coverage             # from the repo root, as CI runs it: both projects plus the coverage floors
                                      # for services/summary.ts and services/dictionary.ts (root vitest.config.ts)
```

The first test run downloads a MongoDB binary (about 100 MB, cached in `~/.cache/mongodb-binaries`).
On an Ubuntu release the downloader does not know yet (26.04 today), set `MONGOMS_DISTRO=ubuntu-2404`.

### Vision eval

`npm run eval:vision -w @healtheat/api` sends the 10 reference photos in `eval/vision/` through
`proposeItems` once each and grades the answers against weighed grams. An item is found when the proposed
items naming it add up to within 2x of its weight. The eval passes when 90% of items are found.
It needs `ANTHROPIC_API_KEY` (or the federation variables below), costs about $0.15 a run and never runs in CI. Rerun it after any change
to the photo prompt, the model or the output schema; `-- --record` saves the run as the baseline in
`eval/vision/baseline.json`. The photos and weights are from Nutrition5k (Google Research, CC BY 4.0).
The recorded baseline found 23 of 23 weighed items on `claude-opus-5-5`. `test/visionEval.test.ts`
grades the rule without calling Claude, and fails when the photo prompt, the model, the photos or their
weighed items change without a new `--record` run.

Without an API key the eval authenticates through workload identity federation. Set
`ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID` and `ANTHROPIC_IDENTITY_TOKEN_FILE`, a file
holding a Google service account ID token minted with
`gcloud auth print-identity-token --impersonate-service-account=<sa> --audiences=https://api.anthropic.com --include-email`.
The Console rule must match that token's audience and pin the account's `sub` and `email`.
